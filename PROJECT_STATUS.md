## Бизнес-контекст

Агентство недвижимости, сдача квартир в аренду. Нанимают удалённых агентов,
чья единственная задача — обзванивать собственников квартир по готовой базе
номеров и договариваться, чтобы они сдавали через это агентство (не через
конкурентов и не сами). Дальше сделку (фото, показ, заселение) ведут другие
люди в команде — зона ответственности агента заканчивается на телефонном
согласии собственника.

Раньше найм и обучение шли вручную: звонок кандидата → собеседование →
насмотр роликов/скриптов → тесты вручную → ручное решение о допуске → ручное
добавление в чаты. Весь этот пайплайн переносим в Telegram-бота.

## Технологии

Python 3, **aiogram 3** (async Telegram Bot framework), SQLite (свой прогресс
кандидатов), конфиг обучения — **YAML** (`training.yaml`), без внешней БД.
Разработка велась в PyCharm на Windows, бот пока не задеплоен (см. раздел
«Деплой» ниже).

## Логика бота (текущая, финальная версия)

```
/start (сбрасывает прогресс и начинает заново, если кандидат уже что-то проходил)
  → "Приступим к обучению?"
  → Видео 1: Презентация работы (ссылка RuTube) → тест (1 вопрос)
  → Видео 2: Мини-курс (ссылка RuTube) → тест (1 вопрос)
  → Скрипт короткий (PDF в Telegram) → "Я ознакомился"
  → Скрипт развёрнутый (PDF) → "Я ознакомился"
  → Почему собственники отказывают (PDF) → "Я ознакомился"
  → Косвенные возражения (PDF) → "Я ознакомился"
  → Тест по всем 4 скриптам (4 вопроса, нужно 3 верных из 4)
  → "Вы уверены, что готовы приступать к звонкам?"
      Да → создаются одноразовые инвайт-ссылки в 3 чата, кандидату присылаются
           ссылки + контакт Рашида, Рашиду — уведомление с результатами тестов
      Нет → прогресс сбрасывается, обучение начинается заново с видео 1
```

Любой непройденный тест — сразу даётся пересдать (retry), кандидат не
блокируется навсегда.

## Ключевые технические решения и почему

- **Видео отправляется через `send_document`, не `send_video`.** Обычная
  отправка видео через Telegram-клиент пережимает файл на стороне
  устройства и на части исходников ломает пропорции кадра (16:9 → похоже на
  4:3). `send_document` передаёт файл байт-в-байт. Из-за этого же видео 1 и
  2 в итоге перевели на внешние ссылки (RuTube) вместо заливки в Telegram —
  так вообще нет проблем со сжатием и лимитом размера файла у Bot API (50 МБ
  на файл при загрузке ботом).
- **Поле `file_id` в `training.yaml` универсальное** — работает и для видео,
  и для PDF. Как получить: отправить файл боту в личку (как файл/документ,
  не через "видео"-режим) от лица Рашида (`admin_chat_id`) — бот ответит
  `file_id`, вставить в нужное поле в yaml.
- **Автоопределение chat_id чатов**: как только бота добавляют в любой чат,
  срабатывает `my_chat_member` хендлер и бот сам пишет Рашиду chat_id этого
  чата — не нужно искать вручную/через сторонние боты.
- **`/start` полностью сбрасывает прогресс** каждый раз (не резюмирует) —
  так удобнее тестировать сценарий заново.
- **Retry-логика в `main()`**: если поллинг падает (сетевая ошибка), бот
  ждёт 10 секунд и пробует снова, вместо того чтобы падать насмерть.

## Известная проблема: связь с Telegram нестабильна на машине разработки

На локальной машине (Windows, PyCharm) соединение с `api.telegram.org`
иногда обрывается (`ConnectionResetError` / `WinError 64`) — похоже на
нестабильную маршрутизацию/подрезание соединений у домашнего провайдера
(частая ситуация в РФ). Диагностика:

- Обычный интернет (Google, GitHub) работает нормально
- `curl` через альтернативный IP Telegram (`149.154.167.220` вместо
  дефолтного `149.154.166.110`) в основном работает, но не 100% стабильно
- Добавлен monkey-patch в `bot.py` (`socket.getaddrinfo`), пробующий
  форсировать резолвинг `api.telegram.org` на этот альтернативный IP — но
  по факту не до конца решил проблему у Python-процесса (возможно, aiohttp
  резолвит DNS в обход этого патча — не до конца продиагностировано)
- Предложенный, но ещё не подтверждённый рабочим тестом фикс: прописать
  `149.154.167.220 api.telegram.org` в hosts-файл Windows
  (`C:\Windows\System32\drivers\etc\hosts`) от администратора — системный
  уровень, должен подействовать надёжнее патча в коде
- **Гипотеза (не проверена)**: на сервере (VDS/хостинг) такой проблемы,
  скорее всего, не будет — датацентры обычно не под той же блокировкой,
  что домашний интернет. Это нужно будет подтвердить по факту после
  деплоя.

## Деплой — ещё не сделан

Пользователь просил перенести бота на **Таймвеб** (Timeweb, хостинг), но
деплой пока отложен — сначала хотели убедиться, что вся логика работает
локально (уткнулись в сетевую проблему выше).

Для деплоя понадобится уточнить у пользователя:
1. Тип тарифа на Таймвебе — VDS/VPS (root по SSH) или shared-хостинг
   (на shared обычно постоянный процесс бота не запустить)
2. Как заходят на сервер — SSH-клиент (PuTTY) или веб-консоль в панели
3. Какая ОС на сервере (предположительно Ubuntu)

После этого — стандартный план: залить проект, `pip install -r
requirements.txt`, `.env` с токеном, запуск через systemd-сервис (чтобы
работал постоянно и поднимался после перезагрузки/краша).
